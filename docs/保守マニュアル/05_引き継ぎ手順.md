# 05 引き継ぎ手順（担当者が交代するとき）

対象: 前任の担当者、後任の担当者、責任者の教員。

予約表の URL（https://miyakyo-music.github.io/yoyaku/）は担当者が替わっても変わりません。掲示物や QR コードはそのままで構いません。

## 今の体制と、引き継ぎの基本方針

- **今の体制**: 開発者（GitHub `kuridanho`）が、卒業後もボランティアで保守を続ける予定です。この文書は、保守を誰かに渡すことになったときのための手順です。
- **アカウントは共有しない**: ログイン情報（ID・パスワード）を渡して1つのアカウントを複数人で使う方法はとりません。Google などは、いつもと違う端末や場所からのログインを不審とみなしてブロックすることがあり、引き継ぎのたびに締め出される恐れがあるためです。
- **代わりに「各自のアカウント＋権限の追加」で引き継ぐ**: 後任者は自分のアカウントを作り、前任者がそのアカウントに権限を与えます。前任者の権限は、引き継ぎが終わってから外します。
- **2人以上で持つ**: どのサービスも、権限の一番強い人（Owner など）が1人だけにならないようにします。1人しかいないと、その人と連絡が取れなくなった時点で誰も設定を変えられなくなります。責任者の教員を、もう1人の持ち主にするのが理想です。

### 使っているサービスと、引き継ぐもの

| サービス | 引き継ぐもの | 方法 | 節 |
| :--- | :--- | :--- | :--- |
| GitHub | Organization `miyakyo-music`（画面のコード・公開） | 後任者を Owner として招待 | A |
| Google ドライブ | スプレッドシート（予約の正本） | 共有ドライブに置き、後任者を追加 | B |
| Google Apps Script | GAS のウェブアプリ（サーバー） | 後任者のアカウントで新しくデプロイし、接続先を差し替え | C |
| （管理画面） | 管理用パスワードなど | 引き継ぎ時に変更 | D |
| Cloudflare（キャッシュを導入した場合だけ） | 読み込みを速くする写しの置き場 | 後任者をメンバーに招待。使わないなら切り替えて外す | G |

## なぜ引き継ぎが必要か

| もの | 誰のものか | 引き継がないと |
| :--- | :--- | :--- |
| GitHub の Organization `miyakyo-music` | Owner（管理者）になっている個人の GitHub アカウント | Owner が全員いなくなると、誰も設定を変えられなくなる |
| スプレッドシート | 置いてある共有ドライブ（またはファイルの持ち主） | 個人の「マイドライブ」にあると、持ち主のアカウントが消えたときにデータごと消える |
| GAS のウェブアプリ | **デプロイした人の Google アカウント**で動く | デプロイした人のアカウントが卒業などで使えなくなると、予約表が「通信に失敗しました」となり止まる |
| 管理用パスワード | GAS のスクリプトプロパティ | 前任者が知ったままになる |

現在の状態（この文書を書いた時点）:

- GitHub の Organization `miyakyo-music` のメンバーは1人（`kuridanho`）だけです。**責任者の教員を含め、Owner を2人以上にしてください。**
- Organization の「2段階認証の必須化」は有効になっていません。（要確認：有効にするかどうか）
- GAS をデプロイしているアカウント: （要確認）
- スプレッドシートの置き場所: （要確認：共有ドライブにあるかどうか）
- 責任者の教員: （要確認）

## 引き継ぎのチェックリスト

卒業・異動の**前**（目安: 毎年3月の初め）に、前任者と後任者がそろって行ってください。

### A. GitHub

- [ ] 後任者が個人の GitHub アカウントを作り、2段階認証を設定する
- [ ] 前任者（Owner）が、github.com の Organization `miyakyo-music` のページ →「People」→「Invite member」で後任者を招待し、Role を「Owner」にする
- [ ] 後任者が招待のメールから参加する
- [ ] Owner が常に2人以上（うち1人は責任者の教員）いることを確かめる
- [ ] 後任者が手元にリポジトリを取得し、開発環境が動くことを確かめる

  ```bash
  git clone https://github.com/miyakyo-music/yoyaku.git
  cd yoyaku
  python3 dev/serve.py
  ```

- [ ] 後任者が、試しに `docs/` などを直して push できることを確かめる（`web/` を直すと本番に公開されるので注意）

### B. Google（スプレッドシート）

- [ ] スプレッドシートが学科または責任者の教員の**共有ドライブ**にあることを確かめる
  - 個人の「マイドライブ」にある場合は、共有ドライブへ移す（移動は、ファイルの持ち主か共有ドライブの権限がある人が行う）。（要確認：大学の Google Workspace で共有ドライブを使えるか）
- [ ] 後任者の大学の Google アカウントを、共有ドライブ（またはスプレッドシート）に追加する（編集できる権限）
- [ ] 後任者がスプレッドシートを開き、メニュー「予約システム」が出ることを確かめる
- [ ] 管理画面の「データベース」ボタンからスプレッドシートを開けることを確かめる
- [ ] 引き継ぎの前にバックアップのコピーを作る（[04_データとバックアップ.md](04_データとバックアップ.md)）

### C. GAS（後任者のアカウントでデプロイし直す）

GAS は「デプロイした人」のアカウントで動くので、後任者のアカウントで**新しいデプロイ**を作り、画面の接続先を切り替えます。

- [ ] 後任者がスプレッドシートのメニュー「拡張機能 > Apps Script」を開く
- [ ] エディタのコードがリポジトリの `gas/Code.gs` と同じか確かめる（違えば貼り付けて保存）
- [ ] 「デプロイ」→「新しいデプロイ」→ 種類の歯車から「ウェブアプリ」を選ぶ
  - 次のユーザーとして実行: 「自分」
  - アクセスできるユーザー: 「全員」
  - 説明: 版の名前（例: `v0.4.0-beta`）
- [ ] 「デプロイ」を押し、権限の確認が出たら後任者のアカウントで「許可」する（「Google で確認されていません」と出たら「詳細」→「（プロジェクト名）（安全ではないページ）に移動」）
- [ ] 表示された新しいウェブアプリの URL（末尾が `/exec`）をブラウザで開き、`{"ok":true,"service":"練習室予約API",...}` と出ることを確かめる
- [ ] リポジトリの `web/config.js` の `window.GAS_API_URL` を新しい URL に書き換え、`main` に push する（GitHub の画面で鉛筆アイコンから編集して「Commit changes」でもよい）
- [ ] 1〜2分後、予約表で予約・取消ができることを確かめる（テスト予約は消す）
- [ ] 前任者のデプロイを「デプロイを管理」で「アーカイブ」する

### D. パスワード

- [ ] 管理画面の「パスワード」タブ →「管理用パスワードの変更」で、新しい管理用パスワード（6文字以上）に変える（またはスプレッドシートのメニュー「予約システム > 管理用パスワードを設定」）
- [ ] 新しい管理用パスワードを、責任者の教員と後任者だけが知る方法で共有する（要確認：学科での保管方法）
- [ ] 限定公開の部屋のパスワードを変えるかどうかを決める（変えたら、使う人に伝え直す）
- [ ] 閲覧パスワードを使っている場合は、変えるかどうかを決める

### E. 前任者の権限の整理（引き継ぎが終わってから）

- [ ] 前任者を GitHub の Organization から外す（卒業後も協力してもらう場合は Member のままでもよい）
- [ ] 前任者の Google アカウントを、共有ドライブ・スプレッドシートの共有から外す（卒業でアカウントが消える場合も、明示的に外しておく）
- [ ] 前任者が手元に持っていたバックアップのコピーなど、個人情報を含むファイルを削除してもらう

### G. Cloudflare（キャッシュを導入した場合だけ）

予約表の読み込みを速くするため、Cloudflare に予約表の写しを置いている場合の手順です。写しなので、ここが無くなっても予約のデータ（正本はスプレッドシート）は失われません。

**引き継ぐ場合**

- [ ] 後任者が自分のメールアドレスで Cloudflare のアカウントを作り、2段階認証を設定する
- [ ] 前任者が Cloudflare の画面「Manage Account > Members」から後任者を招待し、役割を「Administrator」（管理者）にする
  - 「Administrator」は、プログラム・データベースの設定をすべて扱えます。できないのは支払いとメンバーの出し入れだけです。
- [ ] アカウントの持ち主（Super Administrator）も移す場合は、Cloudflare の公式の手順（「Change super administrator」）に従う。画面からできない場合は、Cloudflare のサポートに依頼する
- [ ] GAS が写しを送るときの合言葉を作り直す（GAS の「スクリプトのプロパティ」と Cloudflare の秘密の設定の両方を、同じ新しい値にする。手順は 03_保守・更新手順 のキャッシュの節）
- [ ] 予約表を開き、下の表示で「キャッシュから読み込み」になっていることを確かめる

**引き継がずに外す場合**（後任者が Cloudflare を保守できない、大学の判断で使えない、など）

- [ ] `web/config.js` のキャッシュの接続先を空欄にして `main` に push する（画面は Cloudflare を使わず、GAS から直接読み込むようになる）
- [ ] GAS の「スクリプトのプロパティ」から、キャッシュの送り先と合言葉を消す（GAS が写しを送らなくなる）
- [ ] 予約表で、予約の表示・予約・取消ができることを確かめる
- [ ] Cloudflare の画面で、写しのデータベースとプログラム（Worker）を削除する。必要ならアカウントも閉じる

### F. 書類の更新

- [ ] この保守マニュアルの（要確認）の箇所（担当者名・連絡先など）を新しい担当者の情報に直す
- [ ] 利用者向けガイドの問い合わせ先を直す
- [ ] プライバシーポリシー（`web/privacy.html`）の内容に変更がないか確かめる
- [ ] この文書の「使っているサービスと、引き継ぐもの」の表が、今の構成と合っているか確かめる

## 毎年4月の年度切り替え（引き継ぎとは別に毎年）

1. スプレッドシートのメニュー「予約システム > 前年度の予約をアーカイブ」を実行し、確認で「OK」を押す。
   - 3月31日以前の予約が「予約台帳_YYYY年度」シートへ移ります。4月1日以降の予約は「予約台帳」に残ります。
2. 必要なら、アーカイブのシートを別のスプレッドシートにコピーして保管する。
3. 部屋の増減・名称変更があれば管理画面で直す。
