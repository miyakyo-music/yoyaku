# 03 保守・更新手順

対象: プログラムを直すシステム担当者。git と GitHub の基本操作ができることを前提にします。

システムは「画面（GitHub Pages）」と「サーバー（Google Apps Script）」の2つに分かれていて、**更新のしかたが違います**。

| 変更したもの | 反映のしかた | 反映までの時間 |
| :--- | :--- | :--- |
| 画面（`web/` の中） | `main` ブランチに push するだけ（自動で公開） | 1〜2分 |
| サーバー（`gas/Code.gs`） | 手元で `./dev/gas-deploy.sh`（準備がなければ Apps Script エディタに手で貼り付けて「デプロイを管理」から新しいバージョンに。2章） | すぐ |
| 文書（`docs/`、`README.md`） | push しても公開には影響しない | ― |

## 1. 画面を直して公開する

### 流れ

1. 手元で `web/` のファイルを直す。
2. 開発環境（「6. 開発環境」）で動作を確かめる。スマホの幅（360px・375px）とパソコンの幅の両方で確かめる。
3. コミットして `main` に push する。

   ```bash
   git switch main
   git pull
   # 修正
   git add web/index.html
   git commit -m "（変更内容を日本語で）"
   git push origin main
   ```

4. GitHub Actions のワークフロー「GitHub Pages に公開」（`.github/workflows/pages.yml`）が自動で動き、`web/` の中身を GitHub Pages に公開します。

- ワークフローが動くのは、`main` への push のうち `web/` または `.github/workflows/pages.yml` が変わったときだけです。`docs/` だけの変更では動きません。
- **`main` に push すると、すぐに本番に公開されます。** 試作や大きな見た目の変更は、別のブランチ（例: 以前の `design-unify`）で作業し、確認が取れてから `main` に取り込んでください。
- ワークフローは公開のたびに、`config.js`・`api.js`・部品のフォルダ（`web/index/`・`web/admin/`）の `.js`・`.css`・アイコンの読み込み先に `?v=（コミットの先頭8文字）` を付けます。これで利用者のブラウザに古いスクリプトが残りにくくなります。
- 画面の見た目と動きは、部品ごとのファイルに分かれています（一覧と決まりは仕様書 1.1）。新しいファイルを足したときは、HTML の `<link>`・`<script>` に足します（並び順に意味があります）。

### 公開できたかの確認

1. GitHub のリポジトリの「Actions」タブを開き、いちばん上の「GitHub Pages に公開」が緑のチェックになっていることを確かめる。コマンドで見る場合:

   ```bash
   gh run list -R miyakyo-music/yoyaku -L 3
   ```

2. 予約表（https://miyakyo-music.github.io/yoyaku/）を開いて再読み込みし、画面の下端（フッタ）の版の表示や、直した箇所を確かめる。
3. 反映されないときは [06_トラブルシューティング.md](06_トラブルシューティング.md) の「公開が反映されない」を見る。

- 失敗したとき・手動でもう一度公開したいときは、「Actions」タブ →「GitHub Pages に公開」→「Run workflow」で、`main` を選んで実行できます（`workflow_dispatch`）。

## 2. サーバー（GAS）を直して再デプロイする

`gas/Code.gs` はリポジトリに置いてあるだけで、push しても本番には反映されません（下の「自動で反映する」を設定した場合を除く）。ふだんは、手元のターミナルで次の1つの命令を実行します。Google の `clasp`（Apps Script をターミナルから扱う道具）を使います。

```bash
./dev/gas-deploy.sh
```

やること: GAS の今の中身（`appsscript.json` と `.gs` ファイル）を一時フォルダに取り、`.gs` がちょうど1つならその中身を `gas/Code.gs` で置き換えて送り、今のウェブアプリのデプロイを新しいバージョンに差し替えます（「デプロイを管理」で鉛筆を押して新バージョンにするのと同じ。**URL は変わりません**）。バージョンの説明には、git の短い SHA とコミットの1行目が入ります。

- 送る前に、送り先・差し替えるデプロイ・説明を表示して「本番に反映しますか？」と尋ねます。
- コミットしていない変更がある・`main` ブランチでない・`origin/main` と違うときは、注意を出して続けるか尋ねます。
- GAS 側の `.gs` が2つ以上あるときは、何もせずに止まります（エディタで1つにまとめるか、下の「手で貼り付ける」で）。GAS 側のファイル名は `コード.gs` でも `Code.gs` でも構いません。
- `appsscript.json`（マニフェスト）は、GAS から取ったものをそのまま送り返します。リポジトリの `gas/appsscript.json` は使いません。マニフェストを変えるときは、Apps Script エディタで直します（プロジェクトの設定で「『appsscript.json』マニフェスト ファイルをエディタで表示する」にチェック）。
- デプロイ ID は `web/config.js` の `GAS_API_URL`（`…/macros/s/<デプロイ ID>/exec`）から読みます。
- 確認: GAS の URL（`web/config.js` に書いてあるもの）をブラウザで開き、`{"ok":true,"service":"練習室予約API","apiVersion":1,...}` のように表示されることを確かめる。その後、予約表で予約・取消を1件試し、テスト予約を消しておく。

### 初回の準備（担当者ごとに1回）

1. **Node.js**（20 以上）を入れる（https://nodejs.org/ 。`node -v` で確かめる）。`clasp` は命令の中で `npx` が版を固定して取ってくるので、別に入れる必要はありません。
2. **Apps Script API をオンにする**: GAS をデプロイしている Google アカウントで https://script.google.com/home/usersettings を開き、「Google Apps Script API」をオンにする。
3. **clasp にログインする**: ターミナルで `npx @google/clasp@3.4.1 login` を実行し、ブラウザで同じアカウントを選んで許可する。ホームフォルダに `~/.clasprc.json`（ログインの鍵）ができます。`./dev/gas-deploy.sh` は、ログインしていなければその場でログインするか尋ねます。
4. **スクリプト ID を置く**: スプレッドシートのメニュー「拡張機能 > Apps Script」→ 左の歯車「プロジェクトの設定」→「ID」の「スクリプト ID」をコピーし、リポジトリの `gas/.clasp-script-id` に1行で書く。

   ```bash
   echo "（スクリプト ID）" >| gas/.clasp-script-id
   ```

   スクリプト ID は秘密ではない（それだけでは何もできない）ので、コミットして構いません。コミットしておくと、後任者や下の自動化でもそのまま使えます。ファイルがないと、命令は案内を出して止まります。
5. `./dev/gas-deploy.sh` を実行し、最後に表示される URL で `{"ok":true,...}` が出ることを確かめる。

### 手で貼り付ける（準備ができていないとき・命令が動かないとき）

1. スプレッドシートを開き、メニュー「拡張機能 > Apps Script」を開く（スプレッドシートは管理画面の「データベース」からも開ける）。
2. エディタの `コード.gs`（または `Code.gs`）の中身をすべて消し、リポジトリの `gas/Code.gs` の内容を貼り付ける（Mac なら `pbcopy < gas/Code.gs` でクリップボードに入る）。
3. 保存する（`⌘ + S` / `Ctrl + S`）。**保存しただけでは本番に反映されません。**
4. 右上の「デプロイ」→「デプロイを管理」を開く。
5. 公開中のデプロイ（ウェブアプリ）を選び、鉛筆アイコン（編集）を押す。
6. 「バージョン」で「新バージョン」を選ぶ。説明には版の名前（例: `v0.4.0-beta`）を入れる。
7. 「デプロイ」を押す。

- **「新しいデプロイ」は使わないでください。** 別の URL ができてしまい、`web/config.js` の書き換えが必要になります（担当者の交代のときだけ使います。[05_引き継ぎ手順.md](05_引き継ぎ手順.md)）。
- 設定は「次のユーザーとして実行: 自分」「アクセスできるユーザー: 全員」のままにします（`gas/appsscript.json` の `executeAs: USER_DEPLOYING`、`access: ANYONE_ANONYMOUS` と同じ）。

### 自動で反映する（任意。GitHub Actions「GAS に反映」）

`.github/workflows/gas-deploy.yml` は、`main` に push して `gas/` の中身が変わったとき、試験（`node --test 'dev/test/*.test.js'`）が通ってから `./dev/gas-deploy.sh --ci`（何も尋ねない動かし方）で反映します。次の Secret を登録したときだけ動き、なければ何もしません。

| Secret（Settings > Secrets and variables > Actions） | 中身 |
| :--- | :--- |
| `CLASPRC_JSON` | 初回の準備の3でできた `~/.clasprc.json` の中身をそのまま（Mac なら `pbcopy < ~/.clasprc.json` でコピーして貼る） |
| `GAS_SCRIPT_ID` | スクリプト ID（`gas/.clasp-script-id` をコミットしたなら要らない） |

使う前に、次の危うさを知っておいてください。

- **`CLASPRC_JSON` は、その Google アカウントの Apps Script をすべて書き換えられる鍵です。** このシステム以外のプロジェクトも含みます。リポジトリに書き込める人は、Actions を通じてこの鍵を使えます。できれば、このシステムのためだけのアカウントで使ってください。漏れたかもしれないときは、https://myaccount.google.com/permissions で clasp の許可を取り消し、ログインし直して Secret を入れ替えます。
- **Google のパスワードを変えたとき、許可を取り消したとき、長く使わなかったときなどに鍵が無効になります。** そのときは Actions が失敗して知らせが来るので、手元で `npx @google/clasp@3.4.1 login` し直し、新しい `~/.clasprc.json` の中身で Secret を入れ替えます。
- Apps Script API は**サービスアカウント（人ではない、機械用のアカウント）に対応していません**。そのため、人の Google アカウントの鍵を置くしかありません。
- 自動化を使っていても、手元の `./dev/gas-deploy.sh` はそのまま使えます。

### 画面とサーバーの両方を変えるとき

- 画面とサーバーのやりとりの形を変えるときは、`web/api.js` と `gas/Code.gs` の両方の `API_VERSION`（現在は `1`）を同じ数だけ上げます。
- 順番は **先に GAS を新バージョンでデプロイ → その後で画面を push** です。
- 版が食い違っている間は、利用者の画面の下に「システムが更新されました。ページを再読み込みしてください。」と出ます（`web/api.js` が、応答の `apiVersion` と自分の `API_VERSION` を比べている）。

## 3. 版の上げ方

| 場所 | 何を書くか |
| :--- | :--- |
| `web/api.js` の `window.APP_VERSION` | 画面の版（例: `'v0.4.0-beta'`）。フッタと不具合報告に表示される |
| GAS の「デプロイを管理」のバージョンの説明 | `./dev/gas-deploy.sh` ならコミットの短い SHA と1行目が自動で入る。手で貼り付けるときは同じ版の名前をそろえて書く |
| `API_VERSION`（`web/api.js` と `gas/Code.gs`） | やりとりの形を変えたときだけ上げる（版の名前とは別） |

- 版の名前に `beta` が含まれている間は、予約表の上端に「試験運用中」の帯が出ます。本運用に移るときは `beta` を外した版（例: `v1.0.0`）にすると、帯は自動で消えます（「不具合を報告」はフッタに残ります）。
- 版の付け方の目安: 小さな修正は3つ目の数字（v0.4.0 → v0.4.1）、機能や見た目の大きな変更は2つ目の数字（v0.4.x → v0.5.0）を上げます。（要確認：この付け方を正式なルールにするか）

## 4. タグで版を保存する

公開した版には git のタグを付けておくと、後でその時点の内容をすぐ取り出せます。

```bash
# いまの main に版のタグを付けて GitHub に送る
git switch main
git pull
git tag -a v0.4.0-beta -m "（この版の内容を一言で）"
git push origin v0.4.0-beta

# 付いているタグの一覧
git tag -n
```

- 主なタグ: `v0.3.3-beta`（デザイン統一（Liquid Glass 風）を公開する直前の本番）、`v0.5.4-beta-before-refactor`（リファクタリング前）、`v0.5.7-gas-primary`（予約の正本を Cloudflare に移す前）、`v0.6.1-beta-before-parts`（部品ごとのファイルに分ける前）、`v0.7.1-beta-before-launch-review`。ほかの版のタグとあわせて `git tag -n` で一覧できます。
- 今の版は `web/api.js` の `APP_VERSION` です。版ごとにタグを付けるかは、版を上げるときに決めます。
- タグは一度 push したら付け直さないでください（別の人の手元と食い違います）。

## 5. 元に戻す（安全な方法）

**`git reset --hard` や `git push --force` で履歴を消す方法は使わないでください。** 元に戻す変更を新しいコミットとして追加する方法（`git revert` など）なら、履歴が残り、いつでもやり直せます。

### 直前の1つの修正を取り消す

```bash
git switch main
git pull
git log --oneline -10          # 取り消したいコミットを探す
git revert <コミットのハッシュ>  # 取り消すコミットが自動で作られる
git push origin main           # 1〜2分で公開される
```

### いくつかの修正をまとめて取り消す

```bash
git revert --no-commit <古い方のハッシュ>^..<新しい方のハッシュ>
git commit -m "（取り消した理由）"
git push origin main
```

- 範囲の中に「Merge branch ...」のような合流のコミットが含まれていると、`git revert` は止まります。合流のコミット1つを取り消すときは `git revert -m 1 <ハッシュ>` を使います。

### タグの版まで画面をまるごと戻す

タグ（例: `v0.3.3-beta`）以降には合流のコミットが含まれているため、`git revert` で1つずつ戻すより、`web/` の中身をタグの時点に戻した新しいコミットを作る方が確実です。これも履歴は消えません。

```bash
git switch main
git pull
git restore --source=v0.3.3-beta -- web/
git status                    # 戻ったファイルを確かめる
git commit -m "画面を v0.3.3-beta の内容に戻す（理由）"
git push origin main
```

- サーバー（GAS）も戻す必要があるかを確かめてください。`git diff v0.3.3-beta main -- gas/Code.gs` で違いを見られます。たとえば `v0.3.3-beta` と現在の `main` では、`gas/Code.gs` の違いは不具合報告の件数の数え方だけで、`API_VERSION` はどちらも `1` です。
- 戻した後に再び新しい版を出すときは、`git revert <戻したコミット>` で戻したコミットを取り消せます。

### サーバー（GAS）を前のバージョンに戻す

1. Apps Script エディタの「デプロイ」→「デプロイを管理」を開く。
2. 公開中のデプロイの鉛筆アイコンを押す。
3. 「バージョン」で、戻したい以前のバージョン（説明に版の名前が書いてあるもの）を選ぶ。
4. 「デプロイ」を押す。URL は変わりません。

- エディタのコードは戻らないので、続けて直すときは、リポジトリの該当する版の `gas/Code.gs` を貼り付け直してください（`git show v0.3.3-beta:gas/Code.gs` で取り出せます）。
- `./dev/gas-deploy.sh` で反映していれば、バージョンの説明にコミットの短い SHA が入っているので、どのコミットのコードかがわかります。

## 6. 開発環境（手元で試す）

`dev/serve.py` は、`web/` の画面を配信し、**本物の `gas/Code.gs` をブラウザの中で動かします**。スプレッドシートの代わりにブラウザ（localStorage）に模擬データを保存するので、本番の GAS やスプレッドシートには一切通信しません。

```bash
python3 dev/serve.py
```

| URL | 内容 |
| :--- | :--- |
| http://127.0.0.1:8765/ | 予約表 |
| http://127.0.0.1:8765/admin.html | 管理画面（管理用パスワードは `admin123`。開発環境専用の値） |
| http://127.0.0.1:8765/?reset=1 | 模擬データを初期状態に戻す |

- 初回は `dev/seed.js` が初期セットアップ（`setup()`）を行い、見本の予約と休館を入れます。
- 同じ Wi-Fi のスマホから試すときは `python3 dev/serve.py --lan` で起動し、`http://（このパソコンの IP アドレス）:8765/` を開きます。
- 番号を変えるときは `python3 dev/serve.py 8080` のようにします。
- 仕組み: `dev/serve.py` は `config.js` の代わりに開発用の接続先を返し、HTML に `dev/gas-stub.js`（スプレッドシート・プロパティ・キャッシュ・ロックなどの模擬）、`gas/Code.gs`、`dev/seed.js` を差し込みます。`dev/gas-stub.js` が GAS への `fetch()` を横取りして `doPost` に渡します。
- 模擬なので、Google 側の権限・利用上限・デプロイの設定などは確かめられません。サーバーを変えたときは、本番に出す前に「2. サーバー（GAS）を直して再デプロイする」の確認も行ってください。

## 7. 修正したら確かめること（チェックリスト）

まず試験を流す。このリポジトリの一番上で次を実行する（Node 22 以上。数秒で終わる）。

```bash
node --test 'dev/test/*.test.js'
```

ブラウザを使わずに、テスト環境と同じもの（本物の `gas/Code.gs`・`cache/store.js` と、`dev/` の模擬）を Node の中で動かして確かめる（組み立ては `dev/test/world.js`）。中身は次のとおり。最後に `# fail 0` と出れば通っている。GitHub Actions「試験」でも、`web/`・`gas/`・`cache/`・`dev/` を変えた push と PR のたびに流れる（公開は止めない。失敗するとメールが来る）。

| ファイル | 確かめること |
| :--- | :--- |
| `dev/test/scenario.test.js` | 台本 `dev/compare-scenario.js` を GAS と Cloudflare の両方で流し、手順ごとに同じ結果か。GAS の結果が期待値 `dev/test/scenario.expected.json` と同じか |
| `dev/test/consistency.test.js` | `API_VERSION` が画面と GAS で同じか、JS が文法として読めるか、部品のファイルがすべて HTML から読み込まれ `boot.js`・`fallback.css` が最後か、更新情報（`RELEASES`）の形 |
| `dev/test/mirror-reset.test.js` | 復元のあとの写し直し（`dev/mirror-reset-test.js`） |

期待値と違うと「手順「overlap」が期待値と違う」のように、違った手順の名前と、今の結果・期待値が出る。直したつもりのない違いなら不具合。動きを意図して変えたのなら、違いがその変更のとおりかを確かめてから、`UPDATE=1 node --test 'dev/test/*.test.js'` で期待値を書き直し、変更と同じコミットに入れる。

### 見た目を変えない整理（リファクタリング）をしたとき

CSS の並べ替えや、使っていない指定の削除など、「見た目は変わらないはず」の作業は、`dev/fingerprint.js` で確かめます。全部の要素の「計算後のスタイルと位置」をまとめた指紋を、作業の前と後で比べます。

1. 作業の前に、元に戻せるようタグを付ける（例: `git tag v0.5.4-beta-before-refactor`）。
2. 前の版を `web/__old/` に置くと、前と後を同じテスト環境で並べて開ける（`web/__old/` は git に入らない）。

   ```bash
   mkdir -p /tmp/old && git archive <タグ> web | tar -x -C /tmp/old && cp -R /tmp/old/web/ web/__old/
   printf "window.GAS_API_URL = 'https://script.google.com/macros/s/dev-stub/exec';\nwindow.CACHE_API_URL = 'http://dev-cf.test';\n" > web/__old/config.js
   ```

   前の版は `http://127.0.0.1:8765/__old/index.html`、今の版は `http://127.0.0.1:8765/`。同じ場所（同じデータ）で動く。
3. 前の版を `…/__old/index.html?light&now=2026-10-10T12:00:00` のように時刻を止めて開き（時刻で変わる表示をそろえるため）、開発者ツールのコンソールに `dev/fingerprint.js` の中身を貼り付けて、`await __capture('L1280', ['day', 'book', 'detail', 'room', 'month', 'my', 'bug'])` で基準をとる。
4. 今の版を同じ幅・同じ色・同じ時刻で開き直して、同じ状態の名前で `await __compare(…)`。すべて `'same'` なら見た目は変わっていない。指紋は、読み込みが終わり、小窓が開く動きなどが止まってから測る（動きの途中で測ると、同じコードでも結果が変わったため）。
5. 幅（PC・スマホ）と色（`?light`・`?dark`）と状態（一覧・予約画面・詳細・部屋別・カレンダー・自分の予約・不具合報告・管理画面の各タブ）を一通り比べる。

**CSS だけを変えたとき**は、`dev/css-swap.js` のほうが細かく確かめられる。同じ画面に前の CSS と今の CSS を順に当てて、全要素の計算後のスタイルを比べる。マウスを乗せたとき・押したとき・キーボードで選んだとき、ダーク、小窓を開いた状態、「透明度を下げる」設定、印刷なども、両方の CSS を同じように書き換えて比べる（使い方はファイルの先頭）。部品ごとのファイルに分けたとき（2026-10-11）は、これで予約表・管理画面を PC・iPad・スマホの幅で比べた。

ふだんは `node dev/css-swap-headless.js` で流す。画面に出さない Chrome で、予約表（PC・iPad・スマホ、小窓・予約画面・月表示）と管理画面（PC・スマホ）の場面をまとめて比べ、結果だけを出す（数分。テスト環境が動いていなければ自分で起動する）。前の版は既定で最後のコミット（`--old <タグやコミット>` で変えられる）。すべて同じなら「すべて同じ」と出る。違いがあれば、場面・状態・要素・変わった値を出す。

## 8. 高速キャッシュ（Cloudflare）

予約表の読み込みを速くするため、予約表の写しを Cloudflare に置く仕組みです（仕様書 4.5）。写しなので、壊れても消えても予約のデータ（スプレッドシート）には影響しません。

### 使い始める（最初の1回）

1. Cloudflare のアカウントを作り、2段階認証を設定する（Google で登録した場合は、「パスワードを忘れた」からパスワードを作ってから）。
2. Cloudflare の画面「Storage & Databases > D1」で、データベース `yoyaku-cache` を作る（場所の指定は「Asia-Pacific」）。表示された Database ID を `cache/wrangler.toml` の `database_id` に書く。
3. Cloudflare の画面「My Profile > API Tokens」で、テンプレート「Edit Cloudflare Workers」から API トークンを作る（D1 の編集権限も付ける）。
4. 合言葉（32文字以上のでたらめな文字列。人が考えた言葉は使わない）を1つ作る。Mac のターミナルなら `openssl rand -base64 32 | pbcopy` で作ってクリップボードに入れられる（画面に出さない）。
5. GitHub のリポジトリ「Settings > Secrets and variables > Actions」に次の3つを登録する。
   - `CLOUDFLARE_API_TOKEN`（3 のトークン）
   - `CLOUDFLARE_ACCOUNT_ID`（Cloudflare の画面右側などに出るアカウント ID）
   - `CACHE_PUSH_TOKEN`（4 の合言葉）
6. `main` に push する（または GitHub の「Actions > 高速キャッシュを Cloudflare に公開 > Run workflow」）。公開された URL（`https://yoyaku-cache.〇〇.workers.dev`）をブラウザで開き、`{"ok":true,"service":"練習室予約キャッシュ",...}` と出ることを確かめる。
7. GAS の「プロジェクトの設定 > スクリプト プロパティ」に次の2つを追加する。
   - `CACHE_PUSH_URL` = `https://yoyaku-cache.〇〇.workers.dev/push`
   - `CACHE_PUSH_TOKEN` = 4 の合言葉
8. スプレッドシートのメニュー「予約システム > 高速キャッシュの自動送り直しを設定」を実行し、続けて「高速キャッシュに今すぐ送る」を実行する（「送りました」と出ればよい）。
9. `web/config.js` の `CACHE_API_URL` に `https://yoyaku-cache.〇〇.workers.dev` を書いて `main` に push する。
10. 予約表を開き、更新ボタンにマウスを乗せて「読み込み元: 高速キャッシュ」と出ることを確かめる。

### 使うのをやめる（今まで通りに戻す）

0. 予約の正本を Cloudflare に移している場合は、先に「予約の正本を GAS に戻す」（下の「予約の正本」）を行う。
1. `web/config.js` の `CACHE_API_URL` を `''`（空）にして `main` に push する。予約表は GAS から直接読むようになる。
2. GAS のスクリプト プロパティから `CACHE_PUSH_URL` と `CACHE_PUSH_TOKEN` を消す。GAS は写しを送らなくなる。
3. 必要なら、Apps Script の「トリガー」から `cacheRetry` を消す。GitHub の Secrets 3つを消す。Cloudflare の Worker と D1 データベースを削除する。

### 合言葉を変える（漏れたかもしれないとき・引き継ぎのとき）

1. 新しい合言葉を作り、GitHub の Secrets の `CACHE_PUSH_TOKEN` を書き換えて、Actions の「Run workflow」で公開し直す。
2. GAS のスクリプト プロパティ `CACHE_PUSH_TOKEN` も同じ値に書き換える。
3. メニュー「高速キャッシュに今すぐ送る」で「送りました」と出ることを確かめる。

### おかしいとき

- 予約表に古い内容が出る: メニュー「高速キャッシュに今すぐ送る」を実行する。「送れませんでした」と出たら、合言葉と URL が両方で同じか確かめる（出てくる「GAS の合言葉の長さ」と、Worker の URL を開くと出る `tokenHint` の長さを比べる。違えば、片方に改行や空白が入っているか、途中で切れている。長さが同じでも 401 なら、両方に新しい合言葉を入れ直す）。直らなければ「使うのをやめる」の1だけ行えば、すぐ今まで通りになる（予約の正本を Cloudflare に移していないとき）。
- どちらから読んだか: 予約表の更新ボタンにマウスを乗せると「読み込み元」が出る。

### リアルタイム同期

高速キャッシュは、予約表を開いている画面とつながりっぱなしにして、誰かが予約・変更・取消をしたら「表が変わった」と知らせます（仕様書 2.7・4.5）。追加の設定は要りません（`cache/wrangler.toml` の `durable_objects` と `migrations`）。

- **止めたいとき**: 高速キャッシュ自体をやめれば（`CACHE_API_URL` を空にする）、画面はつなぎに来なくなり、今まで通り60秒ごとの自動更新だけになります。
- **Cloudflare の画面で見るとき**: 「Workers & Pages > yoyaku-cache > Durable Objects」に `Hub` が1つあります。中身は「つながっている画面」だけで、予約のデータは入っていません。

### パスキー（管理画面の Face ID / Touch ID ログイン）

高速キャッシュが、パスキーの署名を確かめる役目も持っています（仕様書 3.3）。高速キャッシュを使っていれば、追加の設定は要りません（`cache/wrangler.toml` の `PASSKEY_RP_ID` と `PASSKEY_ORIGIN` に、予約表のサイトのドメインが入っていること）。

- **使い始める**: 管理画面に管理用パスワードで入り、「設定」タブの「パスキー」で「この端末を登録」を押す。次からはログイン画面の「パスキーでログイン」で入れる。
- **管理者が替わったとき**: 後任者は自分の端末で登録する。前任者のパスキーは一覧から削除する。管理用パスワードも変える。
- **端末をなくしたとき**: ほかの端末（または管理用パスワード）で入り、なくした端末のパスキーを削除する。
- **使うのをやめる**: `cache/wrangler.toml` の `PASSKEY_RP_ID` を `""`（空）にして `main` に push する。管理用パスワードだけで入る今まで通りの形に戻る。高速キャッシュ自体をやめた場合も、自動でパスキーは使えなくなる。
- **予約表のサイトの場所（ドメイン）を変えたとき**: `PASSKEY_RP_ID`・`PASSKEY_ORIGIN` を新しい場所に書き換える。パスキーはサイトの場所に結び付いているので、登録し直しになる。
- 合言葉（`CACHE_PUSH_TOKEN`）を変えると、パスキーでログイン中の人はログインし直しになる（登録は消えない）。

### 予約の正本（Cloudflare に置く）

予約・部屋・設定・休館・不具合報告の正本を、スプレッドシートではなく Cloudflare に置く形です（仕様書 4.6）。書き込みが5秒ほどから0.5秒以下になります。スプレッドシートは写しになり、Cloudflare の変更が数秒〜5分で写ります。**写しのシートを書き換えても予約表には反映されません。変更は管理画面から行います。**

**移す（最初の1回）**
1. `cache/` を含む最新の `main` が Cloudflare に公開されていること（GitHub の Actions「高速キャッシュを Cloudflare に公開」が成功）。
2. `gas/Code.gs` を Apps Script に反映する（`./dev/gas-deploy.sh`。2章）。
3. スプレッドシートのメニュー「予約システム > 高速キャッシュの自動送り直しを設定」を実行しておく（Cloudflare が正本の間は、このトリガーが5分ごとに写しを追いつかせる）。
4. メニュー「予約システム > 予約の正本を Cloudflare に移す」を実行する。1分ほどで「移しました（予約 〇件…）」と出る。失敗したときは「GAS が正本のまま」と出て、何も変わらない。
5. 予約表で予約・取消をしてみて、すぐ終わること、数秒後にスプレッドシートの「予約台帳」に写ることを確かめる。

**GAS に戻す（ロールバック）**
1. メニュー「予約システム > 予約の正本を GAS に戻す」を実行する。Cloudflare の最新の内容でシートを丸ごと写し直してから、GAS で受付を再開する。開いている予約表は、次の操作のときに自動で GAS に切り替わる。
2. 管理用パスワードは、移す前のもの（スクリプト プロパティの `ADMIN_PASSWORD`）に戻る。Cloudflare に移していた間に変えていたら、メニュー「管理用パスワードを設定」で設定し直す。
3. 画面のプログラムごと移す前に戻したいときは、タグ `v0.5.7-gas-primary` を使う（5章「タグの版まで画面をまるごと戻す」）。先に 1 を済ませること。

**おかしいとき**
- スプレッドシートの写しが古い・ずれている: メニュー「Cloudflare から全部写し直す」。
- 予約表で「保存先が切り替わりました」と出る: ページを再読み込みする。
- Cloudflare 側のデータを誤って消した・壊した: Cloudflare は正本（Durable Object の SQLite）を30日前までの任意の時点に戻せる（画面のボタンはなく、`cache/worker.js` に戻すための処理を一時的に足して公開する。Cloudflare のドキュメント「Durable Objects > SQLite storage > Point in time recovery」）。急ぐときは、先に「予約の正本を GAS に戻す」で、写しのシートを正本にして予約の受付を続ける。戻したあとは、必ずメニュー「Cloudflare から全部写し直す」を実行する（写しの続きの番号がずれるため）。番号が戻ったのを写しが見分けて丸ごと写し直す動きは、`node dev/mirror-reset-test.js` で確かめられる（`cache/store.js` の `mirrorChanges` を変えたら流す。7章の試験にも入っていて、GitHub Actions「試験」でも自動で流れる）。

**`gas/Code.gs` の予約・管理の処理を変えたとき**: `cache/store.js` の同じ名前の処理も同じように変える。両方の結果が同じかは、7章の試験（`node --test 'dev/test/*.test.js'`）で確かめる。試験は台本 `dev/compare-scenario.js` を GAS が正本のときと Cloudflare が正本のときの両方で流し、手順ごとに比べる。台本に手順を足したときは、`UPDATE=1` で期待値を書き直す。

ブラウザで流して見比べたいときは、次のようにする（試験と同じ結果になる）。
1. `python3 dev/serve.py` を起動し、ブラウザで http://127.0.0.1:8765/?now=2026-10-10T09:00:00%2B09:00 を開く。
2. ブラウザの開発者ツールのコンソールで `localStorage.clear(); devCf.reset(); location.reload()` を実行してから、`dev/compare-scenario.js` を読み込む（`document.head.appendChild(Object.assign(document.createElement('script'), {src: '/dev/compare-scenario.js'}))`）。結果は `window.__scenario` に入る（GAS で流した結果）。`sessionStorage` などに控えておく。
3. もう一度 1 のように初期化し、コンソールで `migrateToCloudflare()` を実行してから、同じ台本を流す（Cloudflare で流した結果）。2 と同じになればよい。

## 9. アプリのように使う仕組み（sw.js）をやめる

ホーム画面に追加したときの仕組み（Service Worker）で問題が起きたら、`web/sw.js` の中身を次に差し替えて `main` に push します。次に予約表を開いた端末で、保存した画面が消え、仕組みが外れます。

```js
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', (e) => e.waitUntil((async () => {
  for (const key of await caches.keys()) await caches.delete(key);
  await self.registration.unregister();
  for (const c of await self.clients.matchAll()) c.navigate(c.url);
})()));
```

あわせて `web/index/boot.js` の「アプリのように使う」の登録の3行を消します。
