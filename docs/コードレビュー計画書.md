# コードレビュー計画書

宮城教育大学 音楽棟練習室予約システム（yoyaku）における、リポジトリ全体を対象としたコードレビューの計画書です。

---

## 1. 目的と開発特性

本システムは、Claude Code を主軸として開発が進められており、一般的な Web アプリケーションとは異なる明確な設計上の特徴を持っています。

1. **外部依存ゼロの Vanilla JS フロントエンド**:
   `npm` やバンドラー（Webpack, Vite 等）を一切使用せず、純粋な HTML・CSS・ES6+ JavaScript で構成されています。各スクリプトは `<script>` タグの並び順によってブラウザの大域（グローバル）空間で変数を共有して動作します。
2. **二重バックエンド（Dual Master）アーキテクチャ**:
   Google Apps Script（GAS / `gas/Code.gs`）と Cloudflare Workers + Durable Object SQLite（`cache/store.js`）の2つの完全なバックエンド実装を保持し、運用の都合に応じて正本（主系統）を切り替える構成をとっています。
3. **Claude Code 開発規約（`CLAUDE.md`）の存在**:
   平易な日本語のコミットメッセージ・コードコメント、動作変更時の `docs/仕様書.md` 同時改定、利用者向けの更新履歴（`web/index/releases.js` の `RELEASES`）の同時記載、ライト／ダークモード（`html.dark`）の対称性など、厳格な規約が定められています。

本計画書は、これらの特性を踏まえ、AI 支援開発特有の技術的負債（プロンプトごとの CSS 上書き追記、大域名前空間での同名異義関数の発生、例外の安易な握りつぶし、AI 作業用ファイルや機密文書の混入）を網羅的に検知・解消するためのチーム独自のレビュー基準および実施方法を定めます。

## 3. レビュー基準の6つの柱（Review Criteria Pillars）

本リポジトリのアーキテクチャ特性に基づき、以下の 6 つの柱をレビュー基準として定めます。

```
┌────────────────────────────────────────────────────────────────────────┐
│                   コードレビュー基準の 6 つの柱                        │
├─────────────────┬─────────────────┬────────────────────────────────────┤
│ 1. RC-PARITY    │ 二重実装の整合性│ GAS と Store の定数・API・例外一致  │
│ 2. RC-SCOPE     │ 名前空間の保全  │ 大域名前空間の衝突防止・同音異義解消│
│ 3. RC-HYGIENE   │ リポジトリ衛生  │ .gitignore、AI成果物・機密文書の隔離│
│ 4. RC-ERROR     │ エラー・通信安全│ サイレントキャッチ排除・CORS 完全対応│
│ 5. RC-CASCADE   │ CSS 最適化      │ 重複セレクタ統合・!important 抑制  │
│ 6. RC-DOCSYNC   │ 仕様書・版の同期│ 仕様書・更新情報・版番号の完全一致 │
└─────────────────┴─────────────────┴────────────────────────────────────┘
```

### 3.1 RC-PARITY: 二重バックエンドの整合性（Dual-Backend Parity）
- `gas/Code.gs` と `cache/store.js` で提供する同一 API アクションの処理結果、バリデーション規約、定数値が一致していること。
- エラー返却時のエラーコード（`code`）およびユーザー／管理者向けエラーメッセージ文字列が両者で一致していること。
- パスキー（WebAuthn）認証のチケットや署名検証に用いる合言葉（`CACHE_PUSH_TOKEN` / `PUSH_TOKEN`）の命名およびメッセージが整合していること。
- `dev/test/two-implementations.test.js` および `dev/test/scenario.test.js` のテストをすべて通過すること。

### 3.2 RC-SCOPE: 名前空間と大域スコープの保全（Global Scope & Namespace Integrity）
- バンドラーのない Vanilla JS 構成において、`<script>` タグの読み込み順に依存した危険な未定義参照が存在しないこと。
- 各画面（`web/index.html`、`web/admin.html`）において、字下げのないトップレベル変数・関数（`topLevelNames`）が他ファイルと衝突していないこと（`dev/test/consistency.test.js` 準拠）。
- `web/index/` と `web/admin/` の間で同一関数名でありながら振る舞いやシグネチャ・戻り値型が異なる「同音異義関数」（`toast`, `api`, `sessionGet`, `setTime`, `getTime` 等）が存在しない、または明確に名前が区別されていること。
- 共通ヘルパー関数（`pad`, `toMin`, `toHHMM`, `hm`, `esc`, `errMessage`）の勝手な仕様変更がなく、`dev/test/page-helpers.test.js` の同一性テストを維持していること。

### 3.3 RC-HYGIENE: リポジトリおよびツールの衛生管理（Repository & Tooling Artifact Hygiene）
- AI ツール（Claude Code）が生成する設定や内部作業用ディレクトリ（`.claude/`、`.claude/worktrees/`）が `.gitignore` に登録され、リポジトリに誤混入しないこと。
- 過去のレビュー記録など、公開リポジトリにコミットしてはならないセキュリティ上の脆弱性情報を含むファイル（`review/` 等）が確実に `.gitignore` で保護されていること。
- 残存する孤立した Git worktree や一時ファイルが適切に整理されていること。

### 3.4 RC-ERROR: エラーハンドリングと通信の事前確認安全性（Error Handling & Preflight Safety）
- `catch (e) { /* 何もしない */ }` のような、例外の理由を記録も通知もせず握りつぶす記述を原則として排除すること。やむを得ず無視する場合は、その安全性の根拠がコメントで明記されていること。
- `gas/Code.gs` のスプレッドシート単純トリガー（`onEdit` 等）など、権限が制限された環境での失敗がシステム全体の同期不全につながらない設計になっていること。
- Cloudflare Worker（`cache/worker.js`）の CORS 事前確認（OPTIONS プリフライトリクエスト）において、許可メソッドに `POST` を含め、かつ `Access-Control-Allow-Headers` を正しく設定して、ブラウザ標準の API 通信がブロックされないこと。

### 3.5 RC-CASCADE: CSS 詳細度と記述の最小化（CSS Specificity & Minimization）
- プロンプトによる場当たり的な追加によって生じた、同一ファイル内およびファイル間の重複セレクタ定義（`dev/refactor-report.js` が検出する 115 箇所の重複）を統合・整理すること。
- 不必要な `!important` の付与を排除し、詳細度エスカレーションを解消すること（印刷用スタイル `@media print` や `[hidden]` などの意図的な共通定義を除く）。
- ライトモードとダークモード（`html.dark`）の色の対応関係が崩れていないこと（`CLAUDE.md` 準拠）。
- 動的にクラス名が生成されている箇所（`lamp-${st}`, `c-${c.k}`）を誤って「未使用クラス」として削除しないよう、静的解析ツールの限界を考慮すること。

### 3.6 RC-DOCSYNC: 仕様書およびバージョンの完全同期（Specification & Version Alignment）
- システムの振る舞いを変更した場合、必ず同一コミットで `docs/仕様書.md` を更新すること。
- 利用者に関係する変更を行った場合、`web/index/releases.js` の `RELEASES` 配列に適切な日付と内容を追記すること。
- `APP_VERSION`（`web/api.js`）、`API_VERSION`（`web/api.js`, `gas/Code.gs`, `cache/store.js`）、仕様書内の版番号がすべて一致していること。
- コミットメッセージおよびコード内コメントが、専門用語を避けた平易な日本語（`CLAUDE.md` 規約）で記述されていること。

## 4. 指摘事項の優先度分類基準

レビューで発見された課題は、影響度と緊急性に応じて以下の 3 段階に分類します。

| 優先度 | 定義 | 判定基準の例 | 次期対応（M2） |
| :--- | :--- | :--- | :--- |
| **P1（高・重大）** | セキュリティ上の欠陥、通信・データ保全の破綻、致命的な二重実装乖離 | ・機密セキュリティ文書や内部ツールの誤公開リスク<br>・CORS 事前確認失敗による通信ブロック<br>・GAS と Store 間での合言葉や主要エラーの不一致<br>・例外の握りつぶしによるデータ同期遅延 | 原則として本 PR 内で確実に修正する |
| **P2（中・改善）** | 保守性の低下、将来のバグ要因、コードの重複・肥大化 | ・画面間での同名異義関数（引数や戻り値型の不一致）<br>・CSS 重複セレクタによる詳細度混乱<br>・局所的な `!important` の乱用<br>・エラーのサイレントキャッチ | リファクタリング対象として修正を実施する |
| **P3（低・軽微）** | 静的解析ツールの誤検知、補助的なテスト追加、作業ツリーの整理 | ・静的解析スクリプトの動的クラス名ホワイトリスト未登録<br>・エラーメッセージ検証テストの不足<br>・孤立した過去のローカル worktree | 余裕に応じて修正または将来計画として文書化 |

## 5. レビュー実施手順と検証方法

### 5.1 実施手順
1. **ブランチの同期確認**:
   最新の `origin/main`（コミット `e9b6ab8`）から分岐したクリーンなブランチ（`feature/code-review-and-refactoring`）上でレビューを行う。
2. **静的検査と定量指標の計測**:
   `node dev/refactor-report.js` を実行し、CSS 重複セレクタ、未使用疑いクラス、トップレベル変数数、GAS/Store 定数・関数の一致度を計測する。
3. **全コードの精査（6つの柱に基づくチェック）**:
   `web/`, `gas/`, `cache/`, `dev/`, `docs/`, `.github/` の各ファイルを精査し、該当行番号・問題コード・理由・改善案を記録する。
4. **レビュー結果レポートの作成**:
   検出されたすべての課題を整理し、`docs/コードレビュー結果レポート.md` としてドキュメント化する。

### 5.2 独立検証方法（Verification Commands）
レビューおよび後続の修正作業において、以下のコマンドにより品質を保証します。

```bash
# 1. 自動テストスイートの全件パス確認（全32テスト）
node --test 'dev/test/*.test.js'

# 2. リファクタリング指標・静的整合性の確認
node dev/refactor-report.js

# 3. 全 JavaScript ファイルの構文検査
node --check web/*.js web/index/*.js web/admin/*.js cache/*.js dev/*.js dev/test/*.js
```
