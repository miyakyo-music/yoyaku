## 4. 指摘事項の詳細分析と推奨改善案

### 4.1 P1（高・重大な課題）

#### 【F-HYG-01】`.gitignore` における AI 成果物および機密レビュー文書の除外漏れ
- **観点**: `RC-HYGIENE`（リポジトリ衛生）
- **対象ファイル**: `.gitignore` (L1-4)
- **問題箇所のコード**:
  ```gitignore
  .DS_Store
  __pycache__/
  *.pyc
  web/__old/
  ```
- **課題の理由・リスク分析**:
  現在、リポジトリ作業ツリー直下に `.claude/`（設定やローカル Git worktree を内包）および `review/`（過去のレビュー資料一式）が存在していますが、`.gitignore` に記載されていません。
  特に `review/2026-10-20_コードレビュー.md` の冒頭には以下の強い警告が記載されています：
  > `> **この文書の扱い**: 直す前の弱点（認証の試行制限、写しの整合、個人情報の残り方）の詳細が入っています。`  
  > `> リポジトリは公開なので、**コミット・push しないでください**。`
  
  `.gitignore` で除外されていないため、開発者や自動化スクリプトが `git add .` や `git add -A` を実行した際、これらの脆弱性詳細や Claude Code の大量の作業ツリーファイルが誤って公開リポジトリにコミット・push されてしまう重大なセキュリティリスクがあります。
- **推奨改善案（M2 実装方針）**:
  `.gitignore` の末尾に `.claude/` および `review/` を追加します。
  ```gitignore
  .DS_Store
  __pycache__/
  *.pyc
  web/__old/
  .claude/
  review/
  ```

#### 【F-ERR-01】Cloudflare Worker における CORS プリフライト処理の不備
- **観点**: `RC-ERROR`（通信の安全性とエラーハンドリング）
- **対象ファイル**: `cache/worker.js` (L50, L559-564)
- **問題箇所のコード**:
  ```javascript
  // L50:
  if (request.method === 'OPTIONS') return cors(new Response(null, { status: 204 }));

  // L559-564:
  function cors(res) {
    const h = new Headers(res.headers);
    h.set('Access-Control-Allow-Origin', '*');
    h.set('Access-Control-Allow-Methods', 'GET, OPTIONS');
    h.set('Access-Control-Max-Age', '86400');
    return new Response(res.body, { status: res.status, headers: h });
  }
  ```
- **課題の理由・リスク分析**:
  1. `cors()` 関数が返す `Access-Control-Allow-Methods` には `GET, OPTIONS` しか指定されておらず、主たる更新操作である `POST` が含まれていません。
  2. `Access-Control-Allow-Headers` が設定されていません。
  
  ブラウザが `Content-Type: application/json` や認証ヘッダーを伴う `POST` リクエストを送信する際、W3C CORS 仕様に基づきブラウザは事前確認（OPTIONS プリフライト）を送信します。このとき Worker は 204 を返すものの、ヘッダーに `POST` や要求ヘッダーの許可が含まれていないため、ブラウザ側で CORS エラーとなり通信が遮断されます。  
  現在フロントエンド（`web/api.js:86`）が `Content-Type: text/plain;charset=utf-8` を明示してプリフライトの発生を意図的に回避（Simple Request 扱い）しているため表面化していませんが、将来的な通信仕様の標準化や外部クライアント連携において致命的な障害となります。
- **推奨改善案（M2 実装方針）**:
  `cors()` 関数において、`Access-Control-Allow-Methods` に `POST` を追加し、かつ `Access-Control-Allow-Headers` を付与します。
  ```javascript
  function cors(res) {
    const h = new Headers(res.headers);
    h.set('Access-Control-Allow-Origin', '*');
    h.set('Access-Control-Allow-Methods', 'GET, POST, OPTIONS');
    h.set('Access-Control-Allow-Headers', 'Content-Type, Authorization');
    h.set('Access-Control-Max-Age', '86400');
    return new Response(res.body, { status: res.status, headers: h });
  }
  ```

#### 【F-PAR-01】二重バックエンド間におけるパスキー合言葉エラーメッセージの不一致
- **観点**: `RC-PARITY`（二重バックエンドの整合性）
- **対象ファイル**: `gas/Code.gs` (L1028), `cache/store.js` (L1092)
- **問題箇所のコード**:
  - `gas/Code.gs:1028`:
    ```javascript
    if (!key) return fail_('高速キャッシュの合言葉（CACHE_PUSH_TOKEN）が設定されていないため、パスキーは使えません。');
    ```
  - `cache/store.js:1092`:
    ```javascript
    if (!this.memo.ticket) return fail('高速キャッシュの合言葉（PUSH_TOKEN）が設定されていないため、パスキーは使えません。');
    ```
- **課題の理由・リスク分析**:
  管理者向け機能「パスキーの登録・一覧」において、合言葉が未設定だった際のエラーメッセージで参照している設定名が異なります。
  Google Apps Script 側のスクリプトプロパティ、GitHub Actions の Secrets、および仕様書・保守マニュアル（`docs/仕様書.md`, `docs/保守マニュアル/03_保守・更新手順.md`）では一貫して `CACHE_PUSH_TOKEN` と命名されています。  
  Cloudflare Store 側で `PUSH_TOKEN` と表示されると、管理者が保守マニュアルを参照してトラブルシューティングを行う際に「どの設定項目を確認すべきか」混乱を招く原因となります。
- **推奨改善案（M2 実装方針）**:
  `cache/store.js` のメッセージを `gas/Code.gs` および保守マニュアルに合わせ、`CACHE_PUSH_TOKEN` に統一します。
  ```javascript
  if (!this.memo.ticket) return fail('高速キャッシュの合言葉（CACHE_PUSH_TOKEN）が設定されていないため、パスキーは使えません。');
  ```

#### 【F-ERR-02】スプレッドシート単純トリガーにおける例外握りつぶしによる同期不全
- **観点**: `RC-ERROR`（エラーハンドリング）
- **対象ファイル**: `gas/Code.gs` (L1740-1742)
- **問題箇所のコード**:
  ```javascript
  // 高速キャッシュの写しも5分以内に作り直す（シートで閲覧パスワードや限定公開を付けたとき、写しが公開のまま残らないように）
  try { PropertiesService.getScriptProperties().setProperty('CACHE_DIRTY', '1'); } catch (e) { /* 何もしない */ }
  ```
- **課題の理由・リスク分析**:
  Google Apps Script の `onEdit(e)` はユーザーの手動編集時に自動実行される「単純トリガー（Simple Trigger）」です。単純トリガーはセキュリティ上の制約により、`PropertiesService.getScriptProperties()` に対する書き込み権限を持たないケースがあります。  
  権限不足で例外が発生した際、`catch (e) { /* 何もしない */ }` で完全に握りつぶされているため、管理者がスプレッドシート上で直接「閲覧パスワード」や「限定公開」の変更を行っても `CACHE_DIRTY` フラグが立たず、Cloudflare 側のキャッシュが更新されないまま放置される潜在的リスクがあります。
- **推奨改善案（M2 実装方針）**:
  例外を黙殺せず、`console.warn` または実行ログに記録を残すとともに、コメントで「単純トリガー環境で権限がない場合はインストール可能トリガーへの移行または定期実行での補足が必要である旨」の設計意図を明確化します。

### 4.2 P2（中・改善を要する課題）

#### 【F-SCP-01】予約表（index）と管理画面（admin）間における同名関数の意味・シグネチャ乖離
- **観点**: `RC-SCOPE`（名前空間の保全）
- **対象ファイル**:
  - `web/admin/core.js` (L22, L42, L52, L81, L83)
  - `web/index/core.js` (L125, L157), `web/index/data.js` (L8), `web/index/time-wheel.js` (L182, L190)
- **問題箇所のコード**:
  1. `getTime(hSel, mSel)`:
     - `web/index/time-wheel.js:190`:
       ```javascript
       function getTime(hSel, mSel) { return Number(hSel.value) * 60 + Number(mSel.value); }
       // 戻り値: 分単位の「数値」（例: 540）
       ```
     - `web/admin/core.js:83`:
       ```javascript
       function getTime(hSel, mSel) { return toHHMM(Number(hSel.value) * 60 + Number(mSel.value)); }
       // 戻り値: "HH:MM" 形式の「文字列」（例: "09:00"）
       ```
  2. `setTime(hSel, mSel, ...)`:
     - `web/index/time-wheel.js:182`: `setTime(hSel, mSel, min)`（第3引数は分数値数値）
     - `web/admin/core.js:81`: `setTime(hSel, mSel, t)`（第3引数は文字列または数値を `toMin(t)` で変換）
  3. `sessionGet(...)`:
     - `web/index/core.js:125`: `function sessionGet(key) { ... }`（引数でキーを指定）
     - `web/admin/core.js:22`: `function sessionGet() { ... }`（引数なし固定キー `SESSION_KEY`）
  4. `toast(...)`:
     - `web/index/core.js:157`: `toast(message, type, ms, action)`（詳細引数）
     - `web/admin/core.js:42`: `toast(msg)`（単一引数）
  5. `api(...)`:
     - `web/index/data.js:8`: `api(fn, payload, opts)`（第3引数 opts あり）
     - `web/admin/core.js:52`: `api(fn, payload)`（単一ペイロード）
- **課題の理由・リスク分析**:
  同一プロジェクト内のフロントエンドにおいて、全く同一の関数名で異なるシグネチャ・戻り値型（特に `getTime` は数値 vs 文字列）を持つことは、Vanilla JS において認知負荷を高め、将来的なバグの温床となります。  
  なお、`web/index.html` と `web/admin.html` は完全に独立した SPA エントリポイントであり、互いのスクリプトを一切読み込まないため、ブラウザ実行時における大域名前空間の衝突は発生しません（`dev/test/consistency.test.js:84-95` のテストもこれを前提にパスしています）。  
  しかし、将来的に共通コンポーネント（ダイアログや時間ピッカー）を共有・移植しようとした際や、Claude Code がコードを生成する際に、型の取り違えによる重大なランタイムバグ（例: 数値が期待される箇所に文字列が渡り NaN 計算になる等）を引き起こします。

- **【重大なリグレッション警告】`api` 関数の改名禁止**:
  静的解析・整合性テストスイート `dev/test/two-implementations.test.js`（L61-68）では、以下の正規表現を用いて `web/index` と `web/admin` 配下の全 JS ファイルから UI API 操作名を静的抽出して検証しています：
  ```javascript
  for (const dir of ['web/index', 'web/admin']) {
    for (const f of fs.readdirSync(path.join(ROOT, dir)).filter((x) => x.endsWith('.js'))) {
      for (const m of read(dir + '/' + f).matchAll(/\bapi\('([A-Za-z]+)'/g)) web.add(m[1]);
    }
  }
  assert.deepStrictEqual([...web].sort(), store, '画面が呼ぶ操作と、Store の操作の一覧が違う');
  ```
  もし M2 作業者が管理画面側の `api(...)` を `adminApi(...)` 等に改名した場合、管理系 API アクション（`adminGetData`, `adminSaveSettings` 等 11 操作）が `web` 集合から除外され、**`two-implementations.test.js` が即座にテスト失敗（回帰破壊）** します。  
  また前述の通り `web/index.html` と `web/admin.html` は完全に独立した別個の SPA であり、実行時の衝突は物理的に起きません。  
  したがって、**`web/admin/` の `api` 関数名は絶対に改名してはなりません**（現状維持が必須）。同様に `toast` も管理画面の 15 箇所以上で使われており、シグネチャの違いも軽微であるため改名は不要です。

- **推奨改善案（M2 実装方針）**:
  改名対象を、戻り値型やシグネチャが真に食い違っておりランタイムバグの原因となり得る以下の 3 つの関数に厳格に限定します：
  1. `web/admin/core.js` の `getTime(hSel, mSel)` → **`getTimeStr(hSel, mSel)`** に改名（呼び出し元の `web/admin/closures.js`, `settings.js` も合わせて更新）。
  2. `web/admin/core.js` の `setTime(hSel, mSel, t)` → **`setTimeFromStr(hSel, mSel, t)`** に改名（呼び出し元も更新）。
  3. `web/admin/core.js` の `sessionGet()` → **`adminSessionGet()`** に改名。  
  ※ **`api` および `toast` は改名対象から除外（改名禁止）** とします。

#### 【F-ERR-03】通信・キャッシュ状態同期における例外のサイレントキャッチ
- **観点**: `RC-ERROR`（エラーハンドリング）
- **対象ファイル**: `web/api.js` (L75, L113-134 [catch は L129]), `gas/Code.gs` (L1194)
- **問題箇所のコード**:
  ```javascript
  // web/api.js:75:
  if (data && data.adminDevice) { try { localStorage.setItem(DEVICE_KEY, data.adminDevice); } catch (e) { /* 無視 */ } }

  // web/api.js:113-134 (fetchCacheSchedule 関数全体。catch 節は L129):
  const CACHE_TIMEOUT_MS = 2500;
  window.fetchCacheSchedule = async function (range) {
    const base = window.CACHE_API_URL;
    if (!base) return null;
    const ctrl = typeof AbortController === 'function' ? new AbortController() : null;
    const timer = ctrl && setTimeout(() => ctrl.abort(), CACHE_TIMEOUT_MS);
    try {
      const url = `${base.replace(/\/$/, '')}/schedule?from=${encodeURIComponent(range.from)}&to=${encodeURIComponent(range.to)}`;
      const res = await fetch(url, { credentials: 'omit', cache: 'no-store', signal: ctrl ? ctrl.signal : undefined });
      if (!res.ok) return null;
      const data = await res.json();
      if (!data || !data.ok) return null;
      if (data.apiVersion !== API_VERSION) return null; // 写しの形が画面と合わないときは使わない
      if (data.primary) setPrimary(true); // 正本から返ってきた（予約・変更も Cloudflare へ送る）
      return data;
    } catch (e) {
      return null; // L129: 例外が記録されずサイレントに破棄される
    } finally {
      if (timer) clearTimeout(timer);
    }
  };

  // gas/Code.gs:1194 (cachePush_() 内の送信結果プロパティ保存):
  try {
    const next = { CACHE_DIRTY: ok ? '' : '1', CACHE_LAST_ERROR: detail, CACHE_PUSHED_DATE: ok ? today : String(all.CACHE_PUSHED_DATE || '') };
    Object.keys(next).forEach(k => {
      if (String(all[k] || '') === next[k]) return;
      if (next[k]) props.setProperty(k, next[k]); else props.deleteProperty(k);
    });
  } catch (e2) { /* 何もしない */ } // L1194: プロパティ保存の失敗が黙殺される
  ```
- **課題の理由・リスク分析**:
  1. `web/api.js`:
     `fetchCacheSchedule`（L113-134）において、通信タイムアウト（AbortController）、ネットワーク切断、CORS エラー、レスポンスの JSON 解析失敗などのあらゆる例外が L129 の `catch (e) { return null; }` で破棄されています。
     呼び出し元（`web/index/data.js`）は写しが存在しない（正常）のか、通信障害が発生しているのかを判別できず、開発者コンソールにもログが残らないため、エッジキャッシュ通信の不具合調査が困難になります。
     また L75 の `localStorage.setItem` においても例外が理由の記録なしに破棄されています。
  2. `gas/Code.gs`:
     `cachePush_()` 内の L1194 において、Google Apps Script のスクリプトプロパティ（`CACHE_DIRTY`, `CACHE_LAST_ERROR`, `CACHE_PUSHED_DATE`）を更新する処理が `catch (e2) { /* 何もしない */ }` で例外を完全に握りつぶしています。
     プロパティサービスの割当制限超過や一時的エラーが発生した場合にログが一切残らず、エッジキャッシュへの送信状態がスプレッドシート側に正しく反映されなかった原因の追跡が不可能になります（F-ERR-02 と並ぶ例外黙殺箇所）。
- **推奨改善案（M2 実装方針）**:
  - `web/api.js`: `catch (e)` 内で `console.warn('[Cache] スケジュール取得スキップ:', e)` を出力し、開発者ツールから障害要因を即座に追跡できるようにします。
  - `gas/Code.gs`: `catch (e2)` 内で `console.warn('キャッシュ状態プロパティの保存失敗:', e2)` 等のエラーロギングを行い、障害発生時の可観測性を担保します。

## 5. 特筆すべき優れた設計（Good Practices）

今回の精査において、本リポジトリには一般的な Web 開発と比較しても極めて高度で優れた設計・プラクティスが多数存在することが確認されました。これらは今後の改修においても厳格に維持されるべきです。

1. **徹底した XSS（クロスサイトスクリプティング）対策**:
   - `web/index/core.js` および `web/admin/core.js` に実装された `esc()` 関数により、動的 HTML 構築時にすべてのユーザー入力値（氏名、所属、備考など）が漏れなくエスケープされています。
   - `page-helpers.test.js` により、両画面で `esc()` の中身が完全に同一であることが自動保証されています。
2. **SQL インジェクションの完全防御**:
   - Cloudflare Durable Object 内の SQLite（`cache/store.js`）において、すべての SQL 実行が `this.db.exec(sql, ...binds)` を用いたプリペアドステートメント（パラメータバインド）で記述されており、生クエリの結合は皆無です。
3. **二重マスターの自動台本回帰テスト（Scenario Parity Test）**:
   - `dev/test/scenario.test.js` において、GAS と Cloudflare DO SQLite の両方に対して 93 手順に及ぶ一連の予約・競合・キャンセル操作を実行し、各手順の戻り値と Google Sheets 状態がミリ秒単位・プロパティ単位で完全に一致することを自動検証しています。
4. **外部依存ゼロでの Office/PDF 出力エンジン**:
   - `web/admin/export.js` において、外部ライブラリを一切使わず、純粋な JavaScript の `CompressionStream` とバイナリ操作のみで完全な `.xlsx`（ZIP/OpenXML）および ISO-32000 準拠の日本語フォント埋め込み `.pdf` を生成しています。
5. **自己修復および不整合監視インフラ**:
   - `dev/monitor.js` および `dev/mirror-reset-test.js` により、GAS ↔ Cloudflare 間のミラーリング遅延（30分以上の未反映）、バージョン不一致、レプリケーション停止を自動検知して報告・復旧する仕組みが整備されています。
